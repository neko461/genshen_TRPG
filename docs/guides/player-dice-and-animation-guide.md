# 玩家提交检定与骰子动画

在DSH原聊天中使用，不是独立网页战斗台。当前先覆盖剧情检定，战斗仍用原有战斗工具的自动骰。

## 使用

让当前GM重新读取 prompt/gm-system.md 的“公开检定的告知”一节，不新开场、不改卡、不重掷旧结果。下一次剧情检定须用 trpg_check，input.waitForPlayer=true，提供唯一requestId；例如：

```json
{"mode":"solo","slot":"adventure_01","requestId":"player_roll_001","input":{"actor":"pc","attribute":"交涉","tag":"轻小说作家","purpose":"说明这次谈话要达成的目的","difficulty":"普通","risk":"本次行动可预见的风险","waitForPlayer":true}}
```

上例目的和风险仅是占位，不是替当前剧情作决定。角色、标签与场景须真实存在。

宿主会显示“提交回答”卡片：可选“掷骰”让引擎产生2d6，或用自定义回答提交实体骰的两个骰面，例如 `4,3`。不能只提交合计；可选“暂不检定”返回对话。模型不能代填骰面。

提交后显示原生骰子卡片、翻滚落定动画、修正合计和档位。大成功/大失败使用边框强调，无全屏闪烁；系统减少动态效果偏好会关闭动画。“回放动画”仅重播同一结果，不重掷或提交动作。历史卡片默认静态，不因重开聊天而重新结算。

## 状态与边界

- 等待时不写存档、不消耗检定次数。取消、非法输入和缺少回答入口不会降级为自动骰。
- 先在状态副本上验证角色/标签/场景次数并显示修正，结算要求与宣告时相同的revision，避免等待中修改角色后静默变更条件。
- 同一槽位最多一个由本实例发起的等待检定；全工具并发修改仍通过版本检查拒绝旧条件。相同requestId已提交时重放，不再次提问或掷骰。
- 回答等待由DSH宿主管理；中断/重启未结算等待不会消耗次数，但不会凭此实现跨进程持久化的检定队列，需要在原上下文重新说明并发起。
- 不改变2d6结果分档，不把玩家问路、普通闲聊等无实质失败意义的行动强制变成检定。

## 验证

98项回归全部通过（新增6项玩家提交测试），真实DSH19工具检查通过。测试覆盖手动骰面、虚拟骰、等待无写入、取消、非法输入、并发版本变化、重复请求及中止信号。

已重启唯一3081实例并验证原生客户端加载：真实历史检定显示骰面3、4，交涉+2、轻小说作家+1，总和10成功；点击回放出现落定中状态，随后显示同一结果。截图“dice-card-preview.png”。没有发送模型消息或修改真实战役。完整模型发起回答卡片→真人提交→模型叙事仍待首轮体验。

## 补齐战斗检定

玩家角色的攻击、元素技、机制交互和撤退现在也支持战斗工具input.waitForPlayer=true及唯一requestId，提交真实两个骰面后结算。防御等无骰动作直接执行。trpg_combat_attack及trpg_combat act均支持；不使用剧情检定绕过战斗回合。

攻击卡片显示骰面、合计、档位、伤害、目标HP和只读回放。原攻击骰面2、5，灵巧+1，合计8、伤害7、目标HP13已在真实原聊天验证。101项回归及19工具检查通过；新增3项战斗等待测试覆盖无写入、取消、资源扣除、版本变化和幂等重试。完整真人提交仍需后续实际体验。先前“战斗自动骰”限制已解除，已结算的攻击不重掷。

## 2026-10-16：默认等待玩家的宿主保护

实机曾因GM漏传waitForPlayer而直接生成剧情骰。现DSH存在玩家回答服务时，trpg_check与trpg_scene check默认进入提交卡；显式false也不能绕过。玩家的战斗attack/skill/interact/retreat在两个战斗入口同样等待；无骰防御和NPC动作仍直接按规则执行。开发Runtime及无回答UI的本地测试保持原接口，不能把它冒充正式玩家已提交。已有骰点保留，修复只用于后续动作；等待、取消与幂等仍沿用原有保护。
