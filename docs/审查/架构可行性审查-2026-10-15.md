# 架构可行性审查（2026-10-15）

## 结论

现有分层架构可行，值得继续完善；当前实现属于可验证的引擎原型，尚不能视为可稳定连续运行、严格防剧透、完整可回放的 AI GM 系统。不需要整体重写，优先补齐工具层对状态和规则的执行责任。

本次只新增审查报告和操作记忆，没有改动既有代码、设定或正式存档。判断依据是本地文件与实测，不核验同人设定是否符合官方正史。

## 二、优先修复的阻塞问题

### 1. 默认根目录错误（已验证）

- 位置：`code/dsh-trpg/lib/index.js:63–68`。
- 实际：从 lib/index.js 使用 `new URL('../..', import.meta.url)` 得到 `E:\genshen_TRPG\code`，不是工作区根。
- 影响：未设置 TRPG_ROOT 时，设定检索找不到目标资料，存档可能写入 code/save。
- 建议：修正相对层级，并在启动时检查核心文档存在。保留 TRPG_ROOT 覆盖能力。
- 验收：不设置环境变量，也能检索真实设定并把存档定位到项目 save 目录。

### 2. 战斗状态由调用方回填，四轮上限不能可靠执行（已复现）

- 位置：`lib/index.js:445–541`；引擎 `combat.js` 本身能对同一状态执行四轮上限。
- 实际：start 不持久化战斗；attack 使用传入 targetHp 临时构造目标，未更新存档敌人；advance 每次重建状态，roundsCompleted 默认归零，返回值也不含该累计字段。
- 复现：依次传 round=1、2、3、4 而省略累计轮数，第 4 次返回 round=5、over=false。
- 另一个接口缺口：trpg_combat 声明 advance/order 操作，却没有对应分支，会落入 start。
- 建议：按 battleId 保存敌我状态、当前行动者、轮次与阶段。攻击只接收 actorId、targetId 和动作；读取角色、装备和已有判定结果，原子完成扣资源、伤害、状态和事件写入。
- 验收：重启后能继续同一战斗；重复动作不能多扣血；第 4 轮必收场；轮次不能靠传参重置。

### 3. 场景每次重建，检定和恢复没有闭环（已复现）

- 位置：`lib/index.js:566–599`、`engine/scene.js`、`engine/character.js:recover`。
- 实际：open/check/close 各自新建场景。连续 4 次 check 都被接受，close 返回 checkCount=0、outcome=roleplay。
- 实测角色先设为 HP 90/120、能量 1/3，close 声称 energyRestored=true，但角色仍为 HP 90、能量 1。recover 函数也未补上扎营恢复能量的要求。
- 建议：场景持久化并绑定参与者；关闭时依据同一场景的历史检定汇总，并真正执行短休、回能和状态清理。关闭须防重复结算。
- 验收：第 4 次检定被拒；本例首次关闭后 HP 102、能量 3；再次关闭不能重复恢复。

### 4. 剧透闸门只生成提示，没有实际过滤（已复现）

- 位置：`lib/index.js:793–818`、`grepWorkspace`。
- 实际：allowedSpoilerLevels 的结果只被返回；hits 经 map 后直接输出，没有等级或时间线筛选。请求“公开”查询哥伦比娅仍得到深层设定原文。spoilerMax 可直接请求“隐藏”，未与存档上限比较。
- 反例：条目等级为“公开”，也可能带【秘密(GM)】；只解析整条等级仍会泄漏秘密。
- 建议：保留 Markdown 编辑体验，构建包含 id、地区、阶段、公开正文、GM 秘密、暗示文本和解锁条件的结构化索引。未知或未标级内容默认不输出，禁止级仅提供预先审定的间接描述。
- 验收：公开请求不返回隐藏或禁止正文；未到站点不提前暴露未来结果；模型不能通过提高请求级别越过战役上限。

## 三、规则与实现偏差

### 5. 三种建卡方案自身不一致（已验证，需确定规则取舍）

`数值定稿v1.0.md` §2.1 和 README 声称三种分配“总和均为 +3”，但专精 `2+2+0+0−1−1=2`，通才 `1+1+1+1−1−1=2`。`rules.js:49–57` 只允许总和 3 且多重集为均衡方案，实测 BUILD_SCHEMES 中专精、通才均被拒绝。

建议先决定：保留三种分配并接受不同总和，还是调整分配使其总和一致，再同步说明与校验；不能只放宽代码而暗改已定稿的建卡预算。

### 6. 概率表与引擎的精确枚举不符（已验证）

按现有 resolveTier 穷举 36 种骰面，总修正 +2 时：大失败 1/36、失败 5/36、代价成功 15/36、成功 14/36、大成功 1/36；含代价成功率为 30/36=83.3%，不是定稿表的 72.2%。总修正 −3 时原表五档相加超过 100%。

建议从实际判定函数生成表格，并明确“成功率”是否包含代价成功。先修参考表，再依据真实命中、仇恨、装备和旅行者输出评估战斗平衡。

### 7. 装备有计算函数，但未进入角色与战斗的派生数值（部分已复现）

- 实测装备二星生之花后 max_hp 仍为 120，没有变成 150。
- attack 不读取攻击者角色卡、圣遗物与存档目标，仍由调用方给武器、品质、判定档位和目标 HP。
- 套效大多以文字返回，缺乏行动次数、治疗触发、能量上限等执行代码；装备武器的分支还缺少 gear 事件。
- 一星生之花实测返回 hp+30，与定稿“一星仅占位、无加成”冲突。
- 强化统一按 5 量化不适合先攻、仇恨与比例；实测如雷理之冠先攻从 +2 强化一级跳至 +5。
- 法器攻击工具不检查三星门槛，直接打开元素亲和；破防累计缺少 −30 上限。

建议提供统一 deriveStats(character)，按 HP/伤害、先攻、权重、比例分别定义量化，再把被动效果与触发效果接入动作结算。资源取得、强化材料和摩拉不能仅用调用方布尔声明代替实际扣除。

### 8. 状态生命周期与受伤规则尚未落实（静态检查）

冻结、持续伤害、结晶护盾、激化和草原核等主要输出为描述或状态名。没有统一的回合触发与到期处理；结晶护盾在玩家攻击路径中随 statuses 加到目标敌人上，也没有对应命中目标值更新。负减伤被 `Math.max(0, ...)` 截断；实测 25 伤害对 −10 减伤仍造成 25，而非易伤含义下的 35。

建议由状态对象明确来源、持有者、持续轮数、触发时点和消耗条件，结算时统一应用。冻结跳过攻击、DOT 扣血和护盾归属均应由工具执行。

## 四、存档、隔离与可回放

- **会话隔离**：apply 内一个可变 store 被所有注册工具闭包共享，不按聊天会话区分。如果宿主复用同一插件实例，多聊天会互相切换活动槽位；本次未在真实 DSH 中验证实例作用域，属于待集成确认项。
- **覆盖风险**：newCampaign 不拒绝已存在槽位，会重写 campaign 而保留旧 characters/events，形成新旧混档；同 id 建卡也会覆盖旧卡。应默认拒绝，并提供明确的另存为或重置入口。
- **路径边界**：slot 与 lore.file 直接参与 join，没有限制 `..` 或验证解析后的路径仍在许可目录中，可能突破模式隔离和资料范围。应限定合法槽位名、设定目录和文件类型。
- **事务与并发**：单文件临时写后 rename 是好的起点，但角色更新和事件追加不是一笔事务，读改写也没有并发控制；中断可能出现状态已改、事件未记。
- **回放信息不足**：建卡事件仅保存属性等部分信息；武器装备、目标随机选择未完整留事件；场景检定不保存主掷者 id；缺少实际回放还原器。不能据“有 events.jsonl”就认定完整可回放。
- **事件编号与性能**：每次追加重新读取全日志并以有效行数编号，长战役成本随事件累积增长；跳过损坏行后还可能重复 id。应明确报错与修复策略，保留单调序号或唯一 id。

建议短期采用每槽位串行写入、版本检查、完整事件负载与幂等动作编号；确有并发需求时再采用具事务能力的存储。无需为当前规模立即引入远程数据库。

2. team_setting.md 明确单人三人编队、五级好感度；数值定稿按玩家+旅行者并采用四阶关系。额外同伴是否允许、是否计入缩放 n，以及两套关系是否合并，需明确。当前引擎没有实现旅行者动态跟随建卡与元素切换闭环。
3. 稻妻头部写世人记忆已被改写，但时间轴链 E 把改写置于须弥段后；须弥站起始又已是改写后的流浪者状态。需区分“站前既成事实”“站内事件”“站后过渡”，而不是只靠站点数字。
4. 固定主线必须发生与玩家可改变局部结局可以共存，但应列出不可变事件、可变路径及失败推进方式，避免 GM 临场把所有选择强制拉回同一结果。

建议增加一个根目录入口，列出阅读顺序、权威层级、运行条件、存档位置和当前限制；历史文件先建索引再归档，不直接删除或移动。数值常量仍可集中在 rules.js，但目前品质加成、恢复比例和部分反应数值还有重复硬编码，后续应真正收敛到单一来源。
