# 记忆书写规范 —— 给接手本工作区的 AI

> **这份文件是写给 AI 看的。** 开工前请按顺序做三件事：
> ① 读本文件 → ② 读当天的 `memory/logs/YYYY-MM-DD.md`（没有就读最近一份）→ ③ 读 `MEMORY.md` 速查表。
> 读完再动手，能省掉至少一半的重复踩坑。

---

## 0. 六条铁律（违反会出事，不是建议）

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | **先读后写** | 覆盖掉别人（或昨天的自己）刚写的东西 |
| 2 | **日志只追加，绝不覆盖** | 当天过程永久丢失，无法回溯 |
| 3 | **共享区只写自己前缀的文件** | 覆盖他人记忆，跨 AI 协作直接崩 |
| 4 | **写完必须回读验证** | 编辑工具可能静默不落盘，你以为写了其实没写 |
| 5 | **不写密钥、临时路径、搜索结果原文** | 泄密 / 记忆被垃圾塞满 |
| 6 | **Windows 文件名不区分大小写** | 写 `memory.md` 会**覆盖 `MEMORY.md`**，长期笔记全没 |

## 1. 三层记忆体系

| 层 | 位置 | 谁能改 | 装什么 | 什么时候用 |
|---|---|---|---|---|
| **云端** | 自动注入的 profile + 跨会话检索 | **只读，你不能写** | 长期画像、历史对话 | 需要回忆某次具体讨论时，用检索工具查，不要自己存 |
| **用户级** | `~/.workbuddy/MEMORY.md` | 可写 | **跨项目**的用户习惯、硬性偏好 | 用户明确要求长期记住、且跟具体项目无关时 |
| **工作区** | `E：/project` | 可写 | 本项目的架构、进度、坑 | 绝大多数情况都写这里 |

> 判断口诀：**跟项目有关 → 工作区；跟人有关 → 用户级；跟某次对话有关 → 别写，用检索。**

---

## 2. 工作区文件职责

| 文件 | 装什么 | 写入方式 |
|---|---|---|
| `memory/logs/YYYY-MM-DD.md` | **当天流水**：做了什么、为什么这么改、踩了什么坑、实测结果 | **只在末尾追加**（append-only），绝不整体重写 |
| `MEMORY.md` | **长期必知**：架构、路径、端口、铁律、速查表 | 原地编辑，但要收敛（见 §7 长度限制） |
| `memory/项目详细记忆.md` | `MEMORY.md` 放不下的完整细节 | 同上，可长 |
| `shared/` | 跨 AI 交换区（inbox） | **只写自己前缀的文件** |
| `archive/` | 超过 30 天的旧日志 | 一般不写 |

## 3. 该写 / 不该写

**该写**（下次开工必须知道的）

- 架构决策及其**理由**（为什么选 A 不选 B）
- 踩过的坑 + **解法**（含具体命令/代码）
- 用户的明确偏好与项目约定
- 实测数据（改前 vs 改后的对比数字）
- 未解决的遗留问题与下一步

**不该写**

- 搜索结果、网页原文（会过期、占地方）
- 临时文件路径、会话内的中间产物
- 完整报错堆栈（写"什么错 + 怎么修的"就够了）
- 已经在代码里能直接看到的东西
- 重复的结论（写之前先搜一遍有没有）

## 4. 一条好记忆的标准

**结论前置 + 带原因 + 带反例 + 可验证。**

### 坏例子 ❌
```
修复了群聊的问题。
```
问题：不知道修了什么、为什么坏、以后怎么避。三个月后看到等于没有。

### 好例子 ✅
```
### 群聊流 500：闭包变量赋值导致 UnboundLocalError
- 现象：群聊发言直接 500，私聊正常。
- 根因：`group_chat.gen()` 里给外层闭包的 `message` 赋值 → Python 把它当局部变量
  → 读的时候还没绑定 → UnboundLocalError。
- 修法：改用新的局部名，不要给外层闭包变量赋值。
- 验证：单成员/多成员群聊各发一轮，均 200。
```

四要素齐全：**现象 / 根因 / 修法 / 验证**。缺"验证"= 没确认过，标注清楚。

## 5. 格式模板

### 日志（`memory/logs/YYYY-MM-DD.md`）—— 追加到末尾

```markdown
## 标题：动词开头，说清做了什么

### 现象
用户看到了什么 / 原始反馈。

### 根因
为什么会发生。多条就列多条。

### 改动
- 文件 → 具体改了什么
- 备份在哪

### 验证
实测结果，最好有前后对比数字。

### 经验
可复用的结论，写给三个月后的自己看。
```

### 长期笔记（`MEMORY.md`）

```
## 速查表          ← 放最前面，一眼能查到路径/端口/账号
## 一、模块A       ← 按模块分，不按时间分
### ⚠️ 铁律与坑     ← 单独一节，反复踩过的放这里
```

原则：**按主题组织，不按时间组织**。时间维度的东西属于日志文件。

## 6. 本工作区的实测硬坑（必读）

| 坑 | 表现 | 正确做法 |
|---|---|---|
| **编辑工具静默不落盘** | 改完日志显示成功，实际文件没变 | 改关键文件用**脚本化补丁 + `assert` + 改完回读验证**；并行发多个编辑到同一文件必漏 |
| **Windows 大小写不敏感** | `memory.md` == `MEMORY.md` | 新文件名必须**完全不同**，不能只差大小写 |
| **共享代码要防撞车** | 两个 AI 同时改一个文件 | 改前创建 `.beichen_editing`（内容写正在改什么），改完删；看到这个锁就别动 |
| **沙箱里的 Bash 会 PATH 损坏** | `cd` / `ls` / `dirname` 全部 command not found | 改用 Python 完成同等操作（`os.listdir` / `tarfile` / `shutil`） |
| **MEMORY.md 太长会被截断** | 注入时只看到前半段，后半段等于白写 | 控制在几千字符内；细节挪到 `memory/项目详细记忆.md` |
| **远端改代码** | 用 inline `python -c` 写复杂脚本易出错 | 本地写 `.py` → 传上去 → 远端 venv 里跑 → 跑完 `py_compile` 校验 |

## 7. 共享区（`shared/`）约定

- **每个 AI 只写自己前缀的文件**：北辰 `BC_`、津渡 `JD_`。写别人的前缀 = 覆盖别人的记忆。
- **一文件一主题**，别把所有东西塞进一个文件。
- **读完不删**，留作历史。
- 需要对方响应时，在文件里写清楚「要什么」和「为什么」，别只丢一句结论。

---

## 8. 维护节奏

| 周期 | 动作 |
|---|---|
| 每次完成实质工作 | 追加当天日志 |
| 用户明确要求长期记住 | 写 `MEMORY.md` / 用户级 `MEMORY.md` |
| 每 30 天 | 把旧日志按主题蒸馏进 `MEMORY.md`，然后删掉旧日志（或移入 `archive/`） |
| 发现 `MEMORY.md` 过长 | 收敛：合并同类项、删过时条目、细节下沉到 `memory/项目详细记忆.md` |

## 9. 写完自检清单

落笔前逐条对照：

- [ ] 我**先读过**现有内容了吗？（会不会覆盖？）
- [ ] 日志是**追加**的，不是重写的？
- [ ] 共享区里我只动了自己前缀的文件？
- [ ] 回读验证过文件真的落盘了？
- [ ] 有没有写进密钥、临时路径、搜索结果原文？
- [ ] 结论前置了吗？带原因和反例了吗？
- [ ] 三个月后的 AI 看到这条，知道该怎么做吗？
- [ ] 数字/路径/参数是当前的吗？（别写已经改过的旧值）
